# مراجعة أمن النظام (Security Review)

التاريخ: 2026-10-20 · النطاق: الواجهة (React)، قواعد Firestore، ملفات PHP، الاستضافة.

## الخلاصة
النظام عنده طبقة هوية محترمة (Firebase Auth + سجل صلاحيات `authProfiles` موثوق من السيرفر + قواعد تمنع تغيير الأدوار)، **لكن صلاحيات البيانات اليومية (مين يشوف أي عميل) بتتنفذ في المتصفح بس.** أي موظف معاه حساب صحيح يقدر يفتح أدوات المتصفح ويقرأ قاعدة بيانات العملاء كلها. ده أهم ثغرة، وباقي المشاكل أصغر.

## النتائج مرتبة بالخطورة

### 🔴 1. حرجة: السرية في المتصفح مش في السيرفر
- `firestore.rules`: `leads`, `followUps`, `bookings`, `visits`, `purchaseInvoices`, `brokers`, `notBoughtRecords`, `reviewRequests`, `reviewNotes`, `users`, `notifications`: **`allow read: if isStaff()`** لأي موظف نشط، بدون شرط فرع أو موظف.
- كل ما عدا ذلك (`visibleLeads` و`workspace.ts` و`canSeeBranch`) بيتحقق في JavaScript على جهاز الموظف. الموظف بيستخدم نفس مفتاح Firebase العام، فيقدر يكتب `getDocs(collection(db,"leads"))` من الكونسول ويشوف **كل عملاء كل الفروع بأرقام تليفوناتهم وملاحظاتهم ومشترياتهم**، ويصدّرهم.
- الكتابة نفس الشيء: أي موظف يقدر يعدّل أي عميل/متابعة/حجز/فاتورة (يغيّر المسؤول، يزوّر مبالغ، ينسب أحداث لموظف تاني). منع الحذف للمديرين بس.
- **الأثر:** سرقة قائمة العملاء (أهم أصل في البيزنس) وتلاعب بالأرقام.
- **الحل:** تنفيذ التحقق في السيرفر. انظر «قرار مطلوب» تحت.

### 🟠 2. عالية: بيانات العملاء بتتخزن على قرص الجهاز (اتعالجت)
- النسخ القديمة كانت تحفظ نسخة من كل البيانات في `localStorage` (46 مفتاح، نص صريح). لو الموظف قفل المتصفح من غير خروج، ودخل موظف تاني على نفس الجهاز، كان يشوف بيانات الأول لحظيًا.
- **اتصلح:** لا تخزين للبيانات على الجهاز نهائيًا، وبيتمسح أي كاش قديم عند فتح الموقع، والملخص الأسبوعي بقى في `sessionStorage` فقط ويتمسح عند الخروج.

### 🟠 3. عالية: إنشاء حسابات الدخول من المتصفح
- `createStaffLogin` بيعمل الحساب من الواجهة، فلازم التسجيل الذاتي (Sign-up) يفضل مفتوح في Firebase. أي شخص يقدر يعمل حساب Auth (مش هيدخل بيانات لأنه من غير `authProfiles`، لكن بيفتح باب لهجمات إغراق وتخمين).
- **الحل:** نقل إنشاء الحسابات لـ `api/admin.php` (موجود فيه إعادة تعيين كلمة المرور بنفس الأسلوب)، وبعدها تقفل التسجيل الذاتي من Firebase Console. محتاج ملف `crm-firebase-admin.json` على السيرفر.

### 🟡 4. متوسطة: ترويسات الأمان ناقصة (اتصلحت)
لا HSTS ولا X-Frame-Options (Clickjacking) ولا Referrer/Permissions-Policy ولا CSP.
- **اتضاف** في `.htaccess`: HSTS, X-Frame-Options: DENY, nosniff, Referrer-Policy, Permissions-Policy (الميكروفون للموقع بس), COOP.
- **CSP** اتضاف في وضع **Report-Only** (مش بيمنع حاجة). افتح الموقع وراجع الكونسول، ولو مفيش مخالفات حوّل الاسم لـ `Content-Security-Policy`.

### 🟡 5. متوسطة: مفتاح Firebase العام بدون قيود
المفتاح ظاهر في الكود (طبيعي لتطبيقات الويب)، لكن لازم يتقيّد: Google Cloud Console ← APIs & Services ← Credentials ← المفتاح ← Application restrictions: Websites (`shalaby.engsaber.space/*` و`dev-shalaby.engsaber.space/*`) + API restrictions (Identity Toolkit، Firestore، Token Service فقط). ده شغل يدوي منك.

### 🟡 6. متوسطة: صفحة التقييم العامة
- لينك التقييم فيه توكن عشوائي 120 بت (لا يتخمّن)، والقواعد بتسمح بإجابة واحدة فقط بحقول محددة وتقييم 1–5. **مفيش rate limit ولا CAPTCHA**؛ الخطر الفعلي ضعيف لأن التوكن سري، لكن لو اتسرب لينك واحد ممكن يتملّى بتعليق طويل (محدود بـ 1500 حرف).
- **اتصلح:** سكريبت الصفحة بقى ملف خارجي (يتماشى مع CSP) و`no-referrer` عشان التوكن ما يتسربش في الـ Referer.

### 🟢 7. منخفضة (اتعالجت أو سليمة)
- `api/ai.php?find=1` كان بيكشف مسارات السيرفر لأي زائر → **اتشال**. رسايل الخطأ التقنية بقت للمطوّر فقط.
- حقن الصيغ في ملفات CSV: متعالج (بتتهرّب `= + - @`).
- لا `dangerouslySetInnerHTML` ولا `eval`، والتعليقات بتتعرض كنص (مفيش XSS).
- ملفات الأسرار (`crm-ai-secrets.php`، `crm-firebase-admin.json`، سجل الاستهلاك) **خارج** `public_html`، ومجلد `.git` على الموقع محجوب (403).
- مفاتيح Claude وGemini على السيرفر فقط ولا يظهر في الواجهة. endpoint الذكاء الاصطناعي بيتحقق من الموظف النشط ومعدّل الاستخدام محدود.
- GitHub: المستودع عام. مفيش أسرار في الشيفرة أو التاريخ (فقط مفاتيح Firebase العامة)، لكن فكّر تخليه Private.

### ⚪ ملاحظات خصوصية
- أسئلة زكي والملخص الأسبوعي بيبعتوا للذكاء الاصطناعي (Anthropic Claude، والصوت فقط إلى Google Gemini) بيانات العملاء اللي المستخدم يقدر يشوفها (أسماء وأرقام). لازم موافقة العميل/سياسة خصوصية مناسبة حسب قانون حماية البيانات الشخصية المصري.
- Firebase Analytics مفعّل (قياس استخدام عام).

## قرار مطلوب: إزاي نحل الثغرة الحرجة (1)؟

**الخيار أ (الأنسب): قواعد Firestore على مستوى الصف + PHP للعمليات الحساسة**
- القواعد تفرض سيرفريًا: الموظف يقرأ/يكتب عملاءه ومتابعاته بس، مدير الفرع فرعه، المشرف فروعه، المدير العام الكل. نفس منطق `access.ts` لكن بيتنفذ عند جوجل ومش ممكن يتخطّاه المتصفح.
- التطبيق يطلب بيانات نطاقه بس (`where`)، والتحديثات اللحظية تفضل شغّالة.
- PHP يتولى: إنشاء الحسابات وإعادة تعيين كلمات المرور (موجود)، التصدير، الذكاء الاصطناعي، والتقارير المجمّعة.
- الشغل: تعديل القواعد + استعلامات التطبيق + اختبارات قواعد على محاكي Firestore. بيتنفذ على مرحلتين آمنتين (التطبيق الأول ثم نشر القواعد) من غير ما حد يتقفل.

**الخيار ب: كل البيانات عبر PHP API فقط** (Firestore مقفول بالكامل على المتصفح)
- تحكم كامل وسجل تدقيق لكل طلب.
- **التكلفة:** إعادة كتابة طبقة البيانات كلها (مئات الاستدعاءات)، وفقدان التحديث اللحظي (polling)، وتشغيل كل حركة على استضافة مشتركة، وكود PHP جديد لازم يتأمّن بنفس المستوى (حقن، صلاحيات، معدّل). مخاطرته أعلى وبياخد وقت أطول بكتير.

## تحديث: تم تنفيذ الخيار (أ)

- **القواعد:** `firestore.rules` بقت بتفرض النطاق على السيرفر لكل صف: الموظف يقرأ ويكتب عملاءه ومتابعاته وزياراته وحجوزاته وتقييماته بس (أو عميل زميل لو اتكلّف بمتابعة عليه)، مدير الفرع فرعه، المشرف/المشرف العام قائمة فروعه، المدير العام والمطوّر الكل. الوسطاء حسب فروعهم، دليل الموظفين حسب الفرع، سجل العمليات للإدارة العليا بس.
- **التطبيق** بقى يطلب نطاقه فقط (`src/lib/scopes.ts`)، فمفيش بيانات خارج النطاق بتوصل للمتصفح أصلًا.
- **الاختبار:** `rules-tests/` فيه 12 مجموعة اختبارات للقواعد على محاكي Firestore، واختبار للتطبيق الحقيقي على المحاكي بأدوار مختلفة (كلها ناجحة).
- **إنشاء الحسابات** اتنقل لـ `api/admin.php` (`create_login`). لما تحط ملف `crm-firebase-admin.json` على السيرفر، اقفل التسجيل الذاتي من Firebase Console ← Authentication ← Settings ← User actions ← ألغِ «Enable create (sign-up)».

### ترتيب النشر (مهم)
1. النسخة الجديدة من التطبيق تتنشر الأول (بتشتغل مع القواعد القديمة والجديدة).
2. **المطوّر أو المدير العام يفتح التطبيق مرة** بعد النشر: بيكمّل تلقائيًا الحقول الناقصة في البيانات القديمة (فرع سجل العميل، فروع الوسطاء، قوائم فروع المشرفين).
3. بعدها انشر `firestore.rules` من Firebase Console.
